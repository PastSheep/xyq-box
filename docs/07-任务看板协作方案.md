# 07 · DSH 任务看板协作方案

> 探索结论（2026-08，基于 `@linxin666/dsh-client-ui-task-board` 安装副本源码逐文件核实）：
> DSH Web GUI 的「任务看板」可以作为 xyq-box 开发的**活看板 + 真实执行引擎**：
> 每张卡 = 一个可执行的开发任务，点「执行」即驱动一个真实 agent 会话干活。

## 1. 插件能力速览（已验证）

| 能力 | 细节 |
| --- | --- |
| 看板 | 五列：待规划 / 待办 / 进行中 / 已完成 / 已失败；搜索过滤、归档（完成/失败可归档，记录保留） |
| 真实执行 | 卡片 Prompt 经 `session.prompt` 驱动真实 agent；执行中卡片置「进行中」，结算后落「完成/失败」并记录原因 |
| 执行目标钉住 | 每卡可钉 **工作区** / **模式**（agent 预设）/ **权限**（read-only / workspace-write / danger-full-access）；钉不住（如预设被锁、权限命令无人认领）则在发 Prompt **之前**失败，绝不带错设置执行 |
| 定时执行 | 5 段 cron（`分 时 日 月 周`，支持 `*` `/n` `a-b` 逗号表）；浏览器端每分钟 tick |
| 持久化 | 浏览器 localStorage（键 `dsh.taskBoard.v1`），刷新/重启不丢；多标签页经 storage 事件同步 |
| 对 agent 可见 | host 半边注入 SystemPrompt section（`plugin:task-board`），每个 agent 自动知道看板存在与协作方式 |

## 2. 对我们项目开发的价值映射

| 项目需求 | 看板怎么帮 |
| --- | --- |
| M0–M4 里程碑跟踪（docs/06） | 把每个交付物拆成一张卡：待规划→待办→进行中→完成/失败，看板即活清单 |
| 让 agent 干活 | 卡片的执行 Prompt 直接驱动真实 agent 会话；钉工作区 `E:\Projects\xyq-box` 保证落点正确 |
| 权限纪律 | 开发卡钉 `workspace-write` / `danger-full-access`（跑构建、动文件），审查卡钉 `read-only`——钉不住就失败，不会悄悄越权 |
| 代码进 GitHub | 执行 Prompt 末尾约定「完成后 git add -A && commit && push」，工作自动上 origin/main |
| 周期性杂务 | 定时卡：每晚 23:00 生成进度报告 / 跑校验（cron `0 23 * * *`） |
| 可追溯 | 每次执行有记录（会话 id、起止时间、结果/错误），可跳转真实 transcript；归档后仍可查 |

## 3. 推荐用法

### 3.1 拆卡原则

- **一卡一交付物**：M0 的 6 项交付物各一卡；不要用一张卡装整个里程碑（单次执行是一轮 prompt 驱动的会话，任务过大容易跑偏或超时）；
- **Prompt 要自包含**：执行会话是全新上下文，Prompt 里写清「在哪个目录、参照哪份文档、做到什么算完成、完成后如何提交」；
- **钉执行目标**：工作区固定 `E:\Projects\xyq-box`；模式可选（编码任务可用「梁神模式」预设）；权限按任务需要。

### 3.2 卡片种子（可直接粘贴到 GUI）

以下每张卡：**工作区 = `E:\Projects\xyq-box`**；权限默认 `workspace-write`（动仓库文件）；涉及宿主/运行时/构建链时用 `danger-full-access`。

**卡 1 · M0 仓库脚手架**（权限 workspace-write）

```text
在 E:\Projects\xyq-box 搭建 pnpm monorepo 脚手架，严格遵循 docs/05-技术选型与仓库结构.md：
1. 根 package.json + pnpm-workspace.yaml（packages/* 与 apps/*）+ .npmrc（autoInstallPeers=false）；
2. tsconfig.base.json（strict）+ 每个包独立 tsconfig；
3. ESLint + Prettier + Vitest 基础配置；Changesets 初始化；
4. GitHub Actions：typecheck → lint → test → build 四段；
5. cordis 以精确版本 4.0.0-rc.8 锁版（ADR-D1），放 peerDependencies 候选区（M0 内核卡再落定）；
完成后 git add -A && git commit -m 'chore: M0 仓库脚手架' && git push。
```

**卡 2 · cordis 契约测试套件**（权限 workspace-write）

```text
在 E:\Projects\xyq-box 写 cordis 契约测试（ADR-D1 要求，锁 cordis@4.0.0-rc.8）：
用 vitest 固化以下核心用法的行为：new Context()、ctx.plugin(函数/类/对象三种形态)、
inject/provide 依赖驱动（缺失服务→PENDING、卸载 provider→消费者重载）、ctx.effect 清理、
ctx.on/emit、ctx.get 探测、Config 校验失败→fiber FAILED、fiber 状态机流转。
测试放 packages/core/tests/contract/，跑通 pnpm test 为准。
完成后 git add -A && git commit -m 'test: cordis 契约测试' && git push。
```

**卡 3 · @xyq-box/core 内核**（权限 danger-full-access，依赖卡 2 完成）

```text
在 E:\Projects\xyq-box 实现 @xyq-box/core（packages/core），严格遵循 docs/02 与 docs/04：
1. bootstrap(options)：创建 Cordis root Context、读取 plugins.json 清单、装载默认插件集；
2. 插件管理器：清单加载（含本地目录 ./local-plugins/*）、装载/卸载/热重载、fiber 状态诊断接口；
3. 内核内置 connection 服务（RPC 桥，payload 无参数必须传 null）；
4. 单测覆盖装载→卸载→重载；验收：删掉 logger 插件应用不崩、未知服务依赖→PENDING 有诊断。
完成后 git add -A && git commit -m 'feat: M0 内核' && git push。
```

**卡 4 · @xyq-box/sdk + xyq verify**（权限 workspace-write）

```text
在 E:\Projects\xyq-box 实现 @xyq-box/sdk（packages/sdk，纯类型+小工具，零运行时依赖）：
defineView / definePlugin 类型助手、declare module 'cordis' 的 Context 合并助手；
以及 apps/xyq 的 verify 子命令：静态校验插件包 manifest（xyqBox 字段/engine/权限声明/入口存在）。
完成后 git add -A && git commit -m 'feat: M0 SDK 与 verify' && git push。
```

**卡 5 · 示例插件 plugin-hello**（权限 workspace-write）

```text
在 E:\Projects\xyq-box 实现 @xyq-box/plugin-hello（packages/plugins/hello），严格遵循 docs/03-插件规范.md：
含完整 xyqBox manifest、Config schema（schemastery）、inject logger、一个注册到 ctx 的 hello 服务与单测
（装载→卸载→重载）；并写 apps/xyq 的 create 子命令生成同样骨架。
完成后 git add -A && git commit -m 'feat: M0 示例插件与脚手架' && git push。
```

**卡 6 · M0 验收**（权限 read-only）

```text
在 E:\Projects\xyq-box 对照 docs/06 M0 验收标准做只读验收：
1. pnpm install && pnpm typecheck && pnpm lint && pnpm test && pnpm -r build 全部通过；
2. 验收脚本：删掉 logger 插件后启动 → 无日志输出且不崩；
3. 装载依赖未知服务的插件 → PENDING 且诊断可见；
4. 汇总结果与阻塞点，输出验收报告（不修改任何文件）。
```

**定时卡 · 每晚进度报告**（cron `0 23 * * *`，权限 read-only，工作区不钉或钉 xyq-box）

```text
为 E:\Projects\xyq-box 生成开发进度报告：git log --oneline -10、git status、docs/06 里程碑勾选状态、
CI/测试状态（若可查）。输出结构化摘要：已完成 / 进行中 / 阻塞项与下一步建议。只读，不修改文件。
```

### 3.3 使用节奏建议

1. **新里程碑启动**：把该里程碑的交付物批量建卡（卡 1–6 即 M0 全集）；
2. **逐卡执行**：点「执行」→ 卡转「进行中」→ 真实会话干活 → 结算「完成/失败」；失败卡查看执行记录与 transcript 定位原因，修复后「重新执行」；
3. **每日收尾**：定时卡自动生成进度报告；
4. **归档**：完成/失败卡归档，保持看板聚焦当前里程碑。

## 4. 限制与对策

| 限制 | 对策 |
| --- | --- |
| 定时调度在浏览器端，需标签页打开；错过即跳过 | 进度报告类低时效任务可接受；重要任务手动执行 |
| 执行消耗 API 额度 | 拆小卡、复用会话；避免重复失败空跑（先 read-only 审查再执行） |
| 数据在 localStorage（单浏览器、按源隔离） | 定期导出备份（或后续由插件加导出功能）；跨机器不同步 |
| 单次执行 = 一轮 prompt 会话 | 长任务拆卡；多卡可串行依赖（卡 3 依赖卡 2） |
| 权限钉住依赖 `/permission` 命令被会话认领 | 执行前先在会话里验证权限机制可用（当前会话 approval=never 已证明可用） |

## 5. 元层面：它是我们插件规范的活参考

dsh-task-board 是一个可读源码的**真实 client 插件**，对我们（一切皆插件）有几处直接借鉴：

- **host half 极薄**：`src/index.ts` 只注入一条 SystemPrompt section 向 agent 声明插件存在与协作方式——「插件自我声明」模式，我们的内核若未来有 agent 集成可照搬；
- **slots 被占时的退路**：看板因 sidebar/conversation 槽位被内置插件占用，改用 **DOM 注入 + MutationObserver 自愈**——说明「扩展点不足」会逼插件走 DOM hack；**我们的 views 服务应保证扩展点足够丰富**，并把「raw DOM 挂载」作为显式逃生舱（写进 03-插件规范）；
- **纯 client 插件的持久化只能是 localStorage**（DSH 无浏览器可写文件通道）——印证我们 storage 服务抽象的必要性（Web 端 IndexedDB / 桌面端文件系统）；
- **状态机纯函数化**：tasks.ts / schedule.ts 全部 framework-free 纯函数 + 结构型接口注入（structural faces），单测直接驱动——与我们「sdk 零运行时依赖、契约可测」的原则一致。
