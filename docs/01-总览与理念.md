# 01 · 总览与理念

> xyq-box —— 一个「一切皆插件」的独立应用。

## 1. 项目是什么

xyq-box 是一个独立的桌面/Web 应用：**应用的能力边界由插件决定，宿主只提供「装载插件的能力」**。

- **形态**：Web 优先（浏览器内可直接运行整颗内核），可扩展为桌面壳（Electron / Tauri）。
- **内核**：TypeScript + Cordis 4（社区插件运行时）。
- **哲学**：一切皆插件。

## 2. 核心理念：一切皆插件

「一切皆插件」不是口号，它落成三条可验证的设计纪律：

### 纪律一：宿主极简（Thin Host）

宿主壳只做三件事：

1. 创建内核上下文（Cordis root `Context`）；
2. 加载默认插件集（由一份插件清单驱动，而非硬编码逻辑）；
3. 渲染 UI 根（把视图渲染权交给 UI 扩展点聚合的结果）。

更进一步（ADR-D2 定案）：**壳本身也是一个插件**——`plugin-shell-web` / `plugin-shell-desktop` 与业务插件同构，提供系统能力并占据 `root` slot；部署入口（HTML / Electron main）只是调用 `kernel.bootstrap()` 的几行胶水。

任何业务能力——面板、主题、命令、数据源、集成——**不得写在宿主里**，只能以插件形式存在。
宿主代码里出现业务关键词（比如“设置”、“主题”）就是架构违规，评审时直接打回。

### 纪律二：服务即插件（Services are Plugins）

连基础设施都是插件提供的**服务**：

- 配置、日志、存储、UI 扩展点（views）、命令（commands）、权限（permissions）……全部以服务形式由插件提供；
- 每个服务都有**默认实现插件**，也都可以被另一个插件**替换实现**（Cordis 的 `provide` / `inject` 机制天然支持：卸载默认 provider，装载新 provider，所有消费者自动重连到新实现）；
- 服务消费者只声明依赖的服务名（如 `ctx.storage`），**绝不 import 具体实现**；
- 「没有 logger 插件就没有日志」——宿主不粉饰这一点，这正是可裁剪性的来源：发行版可以裁掉任何不需要的基础设施。

### 纪律三：插件是一等公民（First-class Plugins）

- 可安装 / 卸载 / 热重载，运行期生效；
- 生命周期由内核统一管理（加载、依赖等待、卸载清理、失败恢复）；
- 插件声明自己的**依赖**（`inject`）、**能力**（`provide`）、**权限**（`permissions`）与**配置 schema**（`Config`）；
- 第三方插件与内置插件遵循**同一套规范**，没有「特权内置」接口——内置插件只是恰好随发行版一起发布。

## 3. 为什么用 Cordis

Cordis 4 提供了现成的、久经考验的插件运行时语义，我们不需要重造轮子：

| 需求 | Cordis 4 机制 |
| --- | --- |
| 依赖驱动的加载顺序 | `inject` / `provide`；服务缺失时插件停在 **PENDING** 而非崩溃 |
| 可替换实现 | 服务注册是 effect；卸载 provider → 依赖它的插件自动卸载，新 provider 就绪后自动重载 |
| 确定性清理 | 注册类 API 均为 effect；外部资源用 `ctx.effect()` 包裹，卸载时自动释放 |
| 生命周期状态机 | PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED，异常 → FAILED |
| 配置校验 | 插件 `Config` 字段 + Standard Schema（schemastery DSL） |
| 组合与热重载 | `ctx.plugin()` 代码级装载；HMR 重载插件（DSH 生态已有成熟实现可借鉴） |
| 跨 realm 兼容 | `Context.is()` 基于全局 Symbol 判定，允许多副本共存（沙箱/多窗口场景） |

## 4. 目标

1. 内核 + SDK 足够薄，**一个新人半天能写出并装上一个插件**；
2. 默认发行版只含少量内置插件，用户按需增删，可裁剪性可验证（删掉 logger 真的没日志）；
3. 插件协议稳定到「发布即兼容」——见《03-插件规范》的版本与兼容约定；
4. 整个应用的架构可以用一句话讲清楚：**壳 → 内核 → 插件清单 → 一堆插件**。

## 5. 非目标（第一版明确不做）

| 不做 | 原因 / 替代 |
| --- | --- |
| 插件沙箱执行（vm / worker 隔离） | 第一版做**权限声明 + 信任分级**（内置=信任、第三方=受限），沙箱列为远期 |
| 服务端 / 多用户 / 云同步 | 本地优先；后续可插件化引入 |
| 与 DeepSeek Harness 耦合 | 复用其生态模式（插件规范、双端模型），但 xyq-box 是独立项目、独立命名空间 |
| 插件市场基础设施 | M3 先做「本地插件目录 + 远程源」，市场 UI 延后 |

## 6. 命名与术语

- **宿主（Host）**：部署形态对应的薄壳（web / desktop）。
- **内核（Kernel）**：`@xyq-box/core`，Cordis 引导 + 插件管理，不含业务。
- **服务（Service）**：注册在 `ctx` 上的命名能力，由插件提供（`Service` 子类）。
- **插件（Plugin）**：Cordis 插件，函数 / 类 / 对象三种形态之一。
- **Fiber**：一个已装载插件实例的运行时句柄，贯穿其生命周期。
- **Node half / Web half**：一个插件可同时拥有「逻辑端」（Node 环境）与「UI 端」（浏览器环境），两者经 RPC 桥接（详见 02 架构）。
