## 2. 决策记录（ADR，已定案）

> 2026-08 评审定案：D1–D6 全部决议，M0 无阻塞项。决策均有事实依据，见各条「依据」。

### D1 ✅ Cordis 来源：上游 `cordis@4.0.0-rc.8` 精确锁版 + 契约测试

- **问题**：v4 尚在 rc，是否稳定？要不要退回上一正式版（v3）保稳？
- **事实核查**：
  - 版本线：v3 最后正式版 `3.18.1`（2024-09）已维护停滞近两年；v4 自 2024-11（alpha）至今约 21 个月预发布，RC 线 2026-03 起已发 9 个（rc.0 → rc.8，2026-08-10）；
  - **生产实证**：DeepSeek Harness 桌面端（本机每日运行）基于 v4 线 API 生产运行；其 fork `@deepseek-ai/cordis@4.0.1` 于 **2026-08-13 发布（晚于 rc.8 仅 3 天）**，即「上游 rc.8 的稳定版本化裁剪」；
  - **API 同构已验证**：本机解包上游 rc.8 类型文件逐一比对——`Service`（7 个静态 Symbol 完全一致）、`Plugin.Base`（name/Config/inject/provide）、`Inject`、`RegistryService`、`Fiber`、`Context` 与 fork 完全一致；
  - 退回 v3 的代价：v3 是 koishi 时代架构，**没有** Service + Standard Schema、fiber 状态机、inject/provide 依赖驱动语义——本套设计（02/03/04）全部建立在 v4 语义上，回退等于重写架构，并非「保稳」。
- **决议**：**A（上游）**，精确锁 `"cordis": "4.0.0-rc.8"`（不用 ^/~）；M0 交付**契约测试套件**（固化 Context/Service/inject/provide/plugin/effect/fiber 状态等核心用法的行为），作为 4.0.0 正式版升级的迁移闸门；manifest `engine.cordis` 一并声明；
- **后备**：若上游 rc 维护停滞或未来需与 DSH 生态互通，可整体切换到 `@deepseek-ai/cordis@4.0.1`（API 同构，成本仅模块名与 lockfile 变更——由契约测试兜底）；
- **影响**：全仓 `import { ... } from 'cordis'` 与 `declare module 'cordis'` 统一；M0 一旦写死不可混用（Symbol 分裂风险）。

### D2 ✅ 桌面壳：Electron（且壳本身也是插件）

- **问题**：既然「一切皆插件」、桌面壳也是插件，哪个更合适？
- **分析（按插件视角）**：
  - 壳插件需要提供的系统能力：窗口/托盘/文件系统/自动更新，并在 `root` slot 渲染 UI 根；
  - **Electron**：主进程 = Node.js → **内核直接运行在主进程**，壳插件 Node half 用纯 TypeScript 调 Electron API 提供 `system`/`window`/`tray` 服务，Web half 复用 web 壳的渲染层，`connection` 走 Electron IPC。**整个壳插件零第二语言，与其它插件同构**；
  - **Tauri**：系统能力在 Rust 侧——壳插件的每个能力都要写 `#[tauri::command]` 并重建，插件变成 TS+Rust 混合体，内核只能跑在 webview（浏览器 JS），能力桥多一层。违背「插件只用一种语言、壳是普通插件」的哲学，迭代变慢；
  - Tauri 的体积/内存优势真实存在，但与插件哲学正交，不构成取舍理由。
- **决议**：**Electron**；桌面壳 = `@xyq-box/plugin-shell-desktop`（M2），Electron 主进程只做一件事：`kernel.bootstrap()` + 创建窗口；自动更新用 electron-updater；
- **影响**：storage/logger 桌面实现（用户数据目录 + 真实 fs）、打包（electron-builder，nsis/dmg/AppImage）。

### D3 ✅ UI 框架：React

- **决议**：**React 18**（组件生态最大、与 DSH 侧经验一致）；
- **影响**：SDK `defineView` 组件类型基于 React；`react`/`react-dom` 只进 peerDependencies（依赖纪律，05-§5）；样式：CSS 变量 + CSS Modules 起步；views 协议保持框架无关（03-§8 不变），换框架只换适配层。

### D4 ✅ 配置格式：JSON 文件起步

- **决议**：**JSON**——清单 `plugins.json` + 配置分片 `config/<插件id>.json`；Web 端同一结构持久化于 IndexedDB；YAML 阅读器留作插件可选能力；
- **影响**：config 服务实现、迁移工具（JSON→未来格式）。

### D5 ✅ 插件加载器：复用 cordis-loader 模式

- **决议**：**复用**——以 `@deepseek-ai/cordis-plugin-loader`（及上游 cordis 的 loader/组合机制）为参考实现；自研只做薄层：清单解析 + 安装产物路径解析 + engine 校验；
- **影响**：HMR 语义沿用 Cordis 官方；组合语法类 cordis.yml（我们叫 `plugins.json`）。

### D6 ✅ 构建产物：库 tsc / 壳 Vite

- **决议**：库（core/sdk/插件）用 **tsc**（d.ts 齐全、类型可达）；壳与 CLI 用 **Vite/esbuild**（快）；发布 `pnpm pack` 前置校验脚本（对应 DSH 的 verify-pack 经验）；插件暂以编译产物 + d.ts 分发（TS 源码直发留待 M1 评估）；
- **影响**：SDK 类型可达性、插件发布物结构。

## 3. 风险登记

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| cordis v4 未正式发布（rc），API 可能微调 | 中 | 锁版本 + 契约测试（把核心 API 用法固化进单测） |
