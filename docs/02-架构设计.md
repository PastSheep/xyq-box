# 02 · 架构设计

## 1. 分层总览

```
┌──────────────────────────────────────────────────────┐
│  Host 壳（薄）                                        │
│  host-web（浏览器）/ host-desktop（Electron/Tauri）     │
│  职责：启动内核 · 加载默认插件清单 · 渲染 UI 根         │
├──────────────────────────────────────────────────────┤
│  插件生态（能力层）                                    │
│  内置插件（随发行版） + 第三方插件（npm/GitHub/本地目录）│
│  ▸ 业务插件：面板/主题/命令/数据源/集成                │
│  ▸ 基础设施插件：config/logger/storage/views/...      │
├──────────────────────────────────────────────────────┤
│  内核 Kernel（@xyq-box/core）                          │
│  Cordis root Context · 插件管理（装载/卸载/热重载）      │
│  插件清单加载器 · 配置仓库 · 生命周期事件 · 诊断         │
└──────────────────────────────────────────────────────┘
```

关键点：**每一层只依赖下一层**。插件不得依赖具体宿主（不 import host 代码），只依赖内核提供的 `ctx` 与已声明的服务。

## 2. 运行时模型（Cordis 4）

### 2.1 根上下文与内核

内核启动即创建 Cordis 根上下文：

```ts
import { Context } from 'cordis'
const root = new Context()   // 内核唯一持有的根上下文
```

所有插件都装载在根上下文的子作用域上。内核对外只暴露：

- `ctx.plugin(plugin, config)` —— 代码级装载（插件清单加载器最终也走这里）；
- `ctx.inject(deps, callback)` —— 按服务依赖延迟执行；
- `ctx.effect()` / `ctx.on()` —— 生命周期与事件；
- `ctx.get(name)` —— 可选服务探测；
- `ctx.logger(name)` —— 命名日志。

### 2.2 Fiber 状态机（生命周期）

每个已装载插件实例对应一个 fiber，状态由 Cordis 管理：

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                 ↘ FAILED（配置校验失败 / apply 抛错）
```

- **PENDING**：依赖的服务尚未就绪（`inject` 未满足）——插件等待而非崩溃；
- **ACTIVE**：`apply(ctx, config)` 执行完毕；
- **UNLOADING → DISPOSED**：卸载（配置变更 / 热重载 / 显式 dispose / 依赖服务消失），所有 effect 按逆注册序清理，异步 disposer 并发执行；
- **FAILED**：内核记录错误、通知诊断，并保持插件清单中该项为「停用」状态，避免反复崩溃。

### 2.3 依赖与可替换实现

插件通过静态字段声明依赖：

```ts
export const name = 'my-plugin'
export const inject = ['storage', 'logger']   // 硬依赖：全部就绪才 ACTIVE
export const provide = ['reporting']           // 本插件提供的能力
export const Config = /* schemastery schema */  // 配置校验

export function apply(ctx: Context) { ... }
```

**服务替换**是架构的核心动作：

1. 卸载默认 storage provider 插件；
2. 装载第三方 storage 插件（`Service` 子类，注册同名 `ctx.storage`）；
3. 所有 `inject: ['storage']` 的插件自动卸载并重载到新实现上。

→ 这就是「服务即插件」在运行时的落地：**不需要改任何消费者代码，就能换掉任何基础设施。**

## 3. 双端模型：Node half 与 Web half

应用同时存在两个环境：

| 端 | 运行位置 | 职责 |
| --- | --- | --- |
| **Node half**（逻辑端） | 桌面壳主进程 / 浏览器环境的 worker（或直接同线程） | 服务实现、数据处理、持久化、系统能力（fs / 网络 / shell） |
| **Web half**（UI 端） | 渲染线程（DOM） | 视图组件、交互、主题、面板 UI |

一个插件可以同时包含两半（如「文件浏览器」：Node half 做目录遍历，Web half 渲染树形 UI），也可以只有一半（纯逻辑插件 / 纯 UI 插件）。

### 3.1 桥接：connection 服务（RPC）

两半之间通过 `ctx.connection` 服务通信：

- **通道（channel）**：插件自己命名的命名空间，如 `'/filebrowser'`；
- **端点（endpoint）**：通道下的方法名；
- **约定**：payload 必须可 JSON 序列化；**无参数时传 `null` 而非 `undefined`**（`undefined` 会被 JSON 序列化省略键，导致对端 schema 校验失败——DSH 生态实测踩过的坑）；
- **权限**：RPC 端点默认仅限本机回环（loopback），需要更广权限时由 permissions 服务显式放行。

```ts
// Node half：宿主端注册端点
ctx.connection.rpc.handle('/filebrowser', async (endpoint, payload) => {
  if (endpoint === 'list') return { ok: true, value: await walk(payload.path) }
  return { ok: false, error: 'unknown endpoint' }
}, { authority: 'loopback' })

// Web half：UI 端调用
const res = await ctx.connection.rpc.call('/filebrowser', 'list', { path: '/' })
if (!res.ok) { /* 打日志，不静默 */ }
```

## 4. UI 扩展点（views 服务）

壳只渲染「聚合结果」，不感知具体视图：

1. 插件调用 `ctx.views.register(slot, descriptor)` 向扩展点注册视图（面板、工具栏项、状态栏项、命令、右键菜单、主题）；
2. 壳（或 UI 聚合插件）订阅 `ctx.views` 的变更事件，把某 slot 下所有注册项渲染出来；
3. 插件卸载时注册自动撤销（effect 语义），UI 同步消失。

内置 slot（第一版）：

| slot | 含义 | 示例注册者 |
| --- | --- | --- |
| `root` | 应用根区域（通常只由壳或布局插件占据） | host-web |
| `sidebar` / `panel` | 侧边栏与可停靠面板 | 各业务插件 |
| `toolbar` / `statusbar` | 顶栏 / 状态栏 | 命令入口、状态指示 |
| `context-menu` | 右键菜单项 | 文件浏览器等 |
| `theme` | 主题贡献（CSS 变量 + 样式） | 主题插件 |
| `command` | 命令面板条目 | 任何可命令化的操作 |

## 5. 配置与持久化

- **配置 schema**：每个插件声明 `Config`（schemastery DSL），装载时校验，非法配置 → fiber FAILED 且错误可读；
- **配置仓库**：`ctx.config` 服务按插件名分片存储与订阅变更；
- **持久化**：`ctx.storage` 服务抽象——Web 端默认 IndexedDB，桌面端默认用户数据目录 JSON 文件；实现可被插件替换；
- **热更新**：配置变更 → 内核重载受影响插件（沿用 HMR 语义），UI 无需整页刷新。

## 6. 安全模型（第一版）

### 6.1 信任分级

| 级别 | 来源 | 能力 |
| --- | --- | --- |
| **内置（trusted）** | 随发行版发布、签名内置 | 全部权限（含 fs / shell / network） |
| **已安装（installed）** | 用户显式安装的第三方 | 默认受限：**网络、系统命令、敏感文件**需对应 permissions 声明 + 用户确认 |
| **开发（dev）** | 本地目录加载 | 等同 installed；开发者模式可放宽 |

### 6.2 permissions 服务

- 插件 manifest 声明所需权限（`fs.read`、`fs.write`、`network`、`shell`、`storage.global`…）；
- `ctx.permissions` 服务在执行敏感操作前校验；
- 被拒操作抛可读错误，插件可降级或提示用户；
- 沙箱（vm / worker 隔离）列为远期目标，第一版不改变执行模型。

## 7. 插件清单（composition）

内核不硬编码加载顺序，而是消费一份**插件清单**（类 Cordis 的 `cordis.yml`，我们命名为 `xyq-box.config` / `plugins.json`）：

```yaml
plugins:
  - name: '@xyq-box/plugin-logger'      # 默认基础设施
  - name: '@xyq-box/plugin-config'
  - name: '@xyq-box/plugin-storage'
  - name: '@xyq-box/plugin-views'
  - name: '@xyq-box/plugin-commands'
  - name: './local-plugins/my-thing'    # 本地开发目录
    config: { enabled: true }
```

加载顺序由依赖决定（inject），与清单书写顺序无关。清单本身就是用户可编辑的配置——**「应用装了什么」也是一份配置，而不是代码。**

## 8. 典型请求路径（示例：一个按钮）

1. 用户点击面板上的按钮（Web half 组件，由 views 聚合渲染）；
2. 组件调用 `ctx.connection.rpc.call('/my-plugin', 'doThing', payload)`；
3. Node half 端点执行（可能经 `ctx.permissions` 校验）；
4. 结果回传，组件更新视图；若插件被卸载，组件随 effect 一起销毁，不再有悬空调用。

## 9. 架构约束（评审清单）

- [ ] 宿主代码零业务关键词；
- [ ] 插件不 import 宿主包，只依赖 `ctx` 与 `@xyq-box/sdk` 类型；
- [ ] 服务消费者只按名声明依赖，不按实现 import；
- [ ] 一切注册（事件 / 服务 / 视图 / RPC 端点 / 定时器）都是 effect，卸载即清理；
- [ ] RPC payload 可 JSON 序列化，无参数传 `null`；
- [ ] 新能力先进「插件原型」，验证后再固化进内置发行版。
